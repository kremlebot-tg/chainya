# Чайня — сайт чайной

Одностраничный магазин и сайт чайной «Чайня» (Москва, ул. Острякова, 3,
метро Аэропорт). Три языка: русский, английский, китайский. Основная тема —
тёмная, в фирменной палитре чайной.

Основные публичные разделы имеют самостоятельные индексируемые языковые URL:
русский без префикса, English в `/en/`, 中文 в `/zh/`. Canonical, взаимные
`hreflang`, Open Graph и sitemap формируются на сборке; карточки товаров
добавляются в sitemap динамически из опубликованного каталога.

Живой сайт: https://chainya.ru/

## Как устроено

Весь сайт живёт в одном исходнике — `src.html`. Внутри HTML, CSS и JS без сборщиков
и фреймворков. Встроенные `TEA_META` и `I18N.<язык>.teas` дают мгновенный
fallback, а актуальный опубликованный каталог загружается из backend. Владелец
управляет товарами, тремя языками, галереей до восьми фото, ценами и наличием через
`/manage/catalog`. При создании владелец сначала выбирает «Чай» или «Посуда»,
после чего панель показывает только подходящие поля: маркировку и вкусовой
профиль для чая либо материал, размеры, изготовителя и уход для посуды.
Незаполненные поля, фото и языки подсвечиваются, но для обычной карточки не
блокируют публикацию: витрина временно использует доступный перевод. Каталог
разделён на чай и посуду; для посуды доступны чайники, гайвани, пиалы, чахаи, чахэ,
фигурки, инструменты и наборы. Детальные страницы сохраняют это разделение:
чай открывается по `/tea/<id>`, посуда — по `/teaware/<id>`. Также создаются безопасные черновики похожих товаров, выгружается
резервная JSON-копия и просматривается журнал изменений. Для этих изменений
новый релиз сайта не нужен.
Редактируемые блоки страниц вынесены в `/manage/site`. В разделе «Партнёры»
владелец добавляет организации, меняет подписи на трёх языках, порядок и
видимость. Неполные переводы подсвечиваются, но не блокируют публикацию; скрытие
сохраняет запись и историю. Публичный блок «Для бизнеса» читает эти данные из
того же версионируемого хранилища, поэтому изменение партнёров также не требует
релиза кода.
Панель также показывает read-only сверку цен и доступности с Saby и отдельно
считает позиции выбранного прайс-листа сайта и более широкого основного
каталога. Проверка учитывает базовую цену за грамм и отдельную продажную фасовку прайс-листа, но
ничего не применяет автоматически: передача заказов и изменение кассы остаются
отдельными контролируемыми операциями. Новую позицию Saby можно открыть как
скрытый черновик, дополнить фотографиями, категорией и описанием и затем
вручную опубликовать; прайс-лист кассы при этом не изменяется.
Защищённый раздел `/manage/guides` содержит поиск по рабочим инструкциям и FAQ
для самостоятельной работы владельца с заказами, бронями, каталогом, Saby,
Т-Банком, CDEK и резервными копиями.

Клиентский личный кабинет доступен по `/account`: в нём клиент видит свои
заказы и бронирования, меняет имя и пароль. Новые заказы и брони связываются с
кабинетом только при активной защищённой сессии; подробности API и модели
безопасности описаны в [`backend/README.md`](backend/README.md).

Картинки в исходнике помечены маркером `{{img:имя}}` и подставляются при сборке.

## Сборка

```bash
python3 build.py          # один файл: всё вшито внутрь
python3 build.py --web    # раздельные файлы для хостинга → dist/
```

**`build.py`** — для пересылки: один `index.html`, картинки и шрифты вшиты в base64.
Открывается двойным кликом где угодно, работает без интернета и без сервера.

**`build.py --web`** — для сайта: `dist/index.html` плюс `dist/img/` и `dist/fonts/`
отдельными файлами. HTML прилетает сразу, ассеты кэшируются браузером.
Именно `dist/` и публикуется.

Сайт и production checkout разворачиваются одним согласованным релизом:

```bash
./deploy-shop.sh
```

Скрипт локально собирает и проверяет frontend, заранее готовит backend на origin,
включает maintenance только для Chainya и транзакционно переключает обе части.
Общий Nginx не останавливается: при неизменном конфиге он вообще не получает
команду, а при реальном изменении используется только проверенный graceful
reload. До успешного public health доступны автоматические rollback к прежним
symlink и согласованному снимку состояния.
Публичный backend обязан работать с `CHAINYA_TEST_MODE=0`; mock-оплата на
production-vhost недоступна.

Первое применение нового maintenance-конфига и аварийные команды описаны в
[`ops/SAFE_DEPLOY_RUNBOOK.md`](ops/SAFE_DEPLOY_RUNBOOK.md). Это отдельная
production-операция; локальная подготовка файлов её не выполняет.

Telegram-бот публикуется отдельно, но тоже атомарно:

```bash
./deploy-bot.sh
```

Скрипт проверяет общий календарь броней, сохраняет избранное между релизами и
запускает бот от отдельного системного пользователя `chainya-bot`, а не от root.
Исходники, тесты и необходимые медиа бота находятся в `telegram-bot/` внутри
этого же Git-репозитория, поэтому checkout репозитория содержит полный
production-кандидат сайта и бота без зависимости от соседних папок.

Локальные тесты разделены по окружениям: корневой `pytest` проверяет backend,
а тест бота запускается после установки точных зависимостей из
`telegram-bot/requirements.lock.txt`:

```bash
.venv/bin/python -m pytest -q
telegram-bot/.venv/bin/python -m pytest -q telegram-bot/test_bot_booking.py
```

Файлы `requirements*.txt` верхнего уровня зависимостей используются как
читаемая спецификация, а deploy и CI устанавливают проверенные lock-файлы для
Python 3.12. Обновлять lock-файлы нужно осознанно через `uv pip compile` и только
вместе с полным тестовым прогоном.

Перед рекламой, реальным платёжным тестом или внешними записями пройти
[`ops/PRELAUNCH_CHECKLIST.md`](ops/PRELAUNCH_CHECKLIST.md). Проверка сайта сама
по себе не разрешает возвраты, создание отправлений CDEK или передачу заказов в
Saby.

Аварийное восстановление из GitHub и зашифрованной копии бизнес-данных описано в
[`ops/DISASTER_RECOVERY.md`](ops/DISASTER_RECOVERY.md). GitHub хранит весь
воспроизводимый код, но намеренно не содержит SQLite, production env и
загруженные через админ-панель фотографии: для полного восстановления вместе с
commit нужен проверенный off-site recovery bundle.

## Картинки

```bash
./prep_images.sh          # готовит webp из исходных фото
```

Исходники берёт из соседней папки `../source-materials/tea-house`. Нужен `cwebp`
(`brew install webp`).

Осторожно: `cwebp` выбрасывает EXIF, а `sips` поворот не запекает. Кадры с камеры
(4160×2768 с флагом поворота) приходится доворачивать вручную — за это отвечает
пятый аргумент функции `wide`. Без него фото ложатся на бок.

**`extract_logo.py`** вырезает знак «ЧНЯ» из логотипа, снятого поверх фотографии
плантации: берёт самую большую белую область (плашку), заливкой от краёв отсекает фон,
а всё, куда заливка не дошла, считает знаком. Нужен Pillow. Запускать только если
пришлют новый логотип — результат уже лежит в `src-assets/logo-mark.png`.

## Что где

```
src.html            единственный исходник: разметка, стили, скрипты, тексты
build.py            сборка (два режима)
prep_images.sh      фото → webp
extract_logo.py     знак «ЧНЯ» отдельно от фотоподложки
img/                готовые webp
fonts/              Prata и Golos Text, кириллические и латинские сабсеты
src-assets/         логотип, фавикон, картинка для превью ссылок
telegram-bot/       исходники, тесты и медиа Telegram-бота
dist/               результат сборки для хостинга (не в гите)
```

## Шрифты

Prata (заголовки) и Golos Text (текст) — оба Google Fonts, лицензия OFL.
У них нет иероглифов, поэтому китайская версия рисуется системными шрифтами
(правило `:lang(zh)` в стилях).
