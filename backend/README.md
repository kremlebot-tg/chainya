# Checkout backend

Сервер сам считает цены по постоянному каталогу, сохраняет заказы в SQLite и
подключает Т-Банк, CDEK, Saby и Telegram. Тестовая оплата
регистрируется только при явном `CHAINYA_TEST_MODE=1`; в production её маршрутов
нет.

```bash
cd /Users/mac/Desktop/Чайня/site
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements-dev.txt
python3 build.py --web
CHAINYA_TEST_MODE=1 .venv/bin/uvicorn backend.app:app --reload --port 8080
```

Открыть `http://127.0.0.1:8080`. База создаётся в `backend/data/` и не попадает
в Git.

## API

- `GET /api/health` — состояние и число позиций каталога.
- `POST /api/delivery/quote` — актуальный расчёт доставки СДЭК по корзине и городу.
- `POST /api/orders` — серверная проверка, расчёт и сохранение заказа.
- `GET /api/orders/{id}` — состояние заказа.
- `POST /api/account/register`, `POST /api/account/login`, `GET/DELETE /api/account/session` — регистрация, вход, тихая проверка сессии и выход клиента.
- `GET/PATCH/DELETE /api/account` — профиль клиента, изменение имени и удаление кабинета.
- `GET /api/account/orders`, `POST /api/account/orders/claim` — история и защищённая привязка гостевого заказа.
- `GET /api/account/bookings` — бронирования, созданные клиентом после входа.
- `POST /api/orders/{id}/test-pay` — имитация webhook успешной оплаты, только
  при `CHAINYA_TEST_MODE=1`.
- `POST /api/analytics/events` — обезличенное событие сайта без IP, cookies и user-agent.
- `GET /api/bookings/availability?date=YYYY-MM-DD` — свободные получасовые старты на выбранный день.
- `POST /api/bookings` — атомарно сохраняет двухчасовую бронь; при пересечении возвращает `409`.
- `GET /api/admin/dashboard?days=30` — агрегаты, графики, воронка и состояние систем.
- `GET /api/admin/catalog` — полный каталог для панели владельца.
- `POST /api/admin/catalog/items`, `PUT /api/admin/catalog/items/{id}` — добавление и изменение товара.
- `PUT /api/admin/catalog/order` — порядок товаров на витрине.
- `POST /api/admin/catalog/items/{id}/image?revision=N` — проверка и загрузка фотографии.
- `GET /api/admin/orders?q=&status=&limit=50&offset=0` — поиск и постраничная очередь заказов.
- `GET /api/admin/business-leads?q=&status=&limit=50&offset=0` — поиск и постраничные B2B-заявки.
- `GET/POST /api/admin/booking-blocks`, `DELETE /api/admin/booking-blocks/{id}` — ручное закрытие и открытие времени владельцем.
- `GET /api/admin/saby/status` — готовность конфигурации Saby без раскрытия секретов.
- `POST /api/admin/saby/test` — проверка авторизации и получение точек продаж.
- `GET /api/admin/saby/catalog-preview` — до 50 позиций выбранного прайс-листа.
- `GET /api/admin/saby/catalog-shadow?history_limit=10` — последний read-only
  отчёт сравнения сайта с Saby и ограниченный журнал запусков.
- `POST /api/admin/saby/catalog-shadow/run` — ручная теневая сверка без изменения
  сайта, кассы, цен, остатков или заказов.
- `GET /api/admin/integrations/status` — сетево-независимая готовность Т-Банка, Saby и CDEK.
- `GET /api/admin/orders/{id}/integration-preview?ready_at=YYYY-MM-DD HH:MM:SS` —
  предварительные входные данные интеграций без внешних запросов и записей.

В production стоимость и доступность доставки рассчитываются через CDEK API,
а платежи создаются через Т‑Банк. Mock-оплата существует только при явном
`CHAINYA_TEST_MODE=1` и недоступна на production-vhost. Секреты передаются
только через защищённые переменные окружения.

Подготовительные адаптеры находятся в `tbank.py`, `cdek.py` и `saby_sync.py`.
Они ничего не запускают при импорте. Все будущие внешние записи обязаны идти
через `IntegrationWriter`: единый guard запрещает их в `CHAINYA_TEST_MODE`, при
неопубликованном workflow и в режимах `off`/`shadow`. Только точное значение
`CHAINYA_TEST_MODE=0` отключает тестовый предохранитель; опечатки остаются в
безопасном тестовом режиме.

Панель владельца открывается по `/manage`. Ключ вводится на отдельной странице
входа и проверяется сервером. После успешной проверки сервер выдаёт
`HttpOnly; Secure; SameSite=Strict` cookie на 12 часов; сырой ключ не хранится
в JavaScript и браузерном хранилище. Старые ссылки `/manage#ADMIN_TOKEN` и
`/admin/orders#ADMIN_TOKEN` остаются переходным способом входа: минимальная
страница отправляет ключ серверу, сразу удаляет fragment из адреса и получает
ту же защищённую сессию. Без сессии полноценная HTML-оболочка панели не
выдаётся. Выход выполняется кнопкой в правом верхнем углу.

### Управление каталогом

Раздел `/manage/catalog` использует ту же защищённую сессию. В нём можно менять
название, происхождение и описание на русском, английском и китайском, цену,
единицу продажи, наличие, публикацию, категорию, вкусовой профиль, фотографию и
порядок товаров. Для каждой локали также предусмотрены поля маркировки:
состав, изготовитель/упаковщик/импортёр, срок годности и условия хранения.
Пустые поля не показываются покупателю; перед публикацией пищевого товара их
нужно заполнить по фактической этикетке, не по предположению. Удаление намеренно заменено безопасным переключателем
«Показывать на сайте»: скрытая позиция исчезает с витрины и не принимается в
новых заказах, но остаётся в истории.

Production-каталог хранится в `/var/lib/chainya-shop/catalog.json`, фотографии —
в `/var/lib/chainya-shop/catalog-media/`. Оба ресурса переживают новые релизы и
попадают в ежедневную резервную копию. При первом запуске каталог атомарно
создаётся из `backend/catalog.seed.json`; последующие релизы пользовательские
изменения не перезаписывают. Витрина получает опубликованный каталог из
`GET /api/catalog`, а встроенные данные `src.html` остаются fallback на случай
недоступности API.

Исходный seed пересобирается после намеренного изменения встроенного fallback:

```bash
python3 scripts/build-catalog-seed.py
```

Редактор не включает синхронизацию Saby и не меняет кассовый прайс-лист.

### Личный кабинет клиента

Кабинет открыт по `/account`. Клиент регистрируется по номеру
телефона и паролю длиной не менее 10 символов. Пароль хранится только как
PBKDF2-SHA256-хеш с отдельной случайной солью. После входа сервер выдаёт
случайную сессию в `HttpOnly; SameSite=Strict` cookie: на production она также
имеет флаг `Secure`, действует 30 дней, а в SQLite хранится только хеш токена.

Заказ или бронь с сайта автоматически связываются с кабинетом, только если они
созданы во время действующей клиентской сессии. Совпадение телефонных номеров
само по себе никогда не открывает старые записи. Гостевой заказ можно присоединить через
кнопку на защищённой странице результата оплаты: сервер требует одновременно
номер заказа, его непубличный token и клиентскую сессию. Уже привязанный к
другому кабинету заказ перенести через публичный API нельзя.

В кабинете доступны до 100 последних заказов и броней, состав, сумма, статусы и
ссылка на ещё не завершённую оплату. Клиент может изменить отображаемое имя и
пароль, выйти или удалить кабинет. Смена пароля завершает остальные сессии.
Удаление кабинета удаляет профиль и сессии и отвязывает историю, но не удаляет
саму запись заказа: сроки хранения заказа определяются требованиями учёта и
политикой конфиденциальности. Восстановление забытого пароля до подключения
проверенного SMS/email-канала выполняется через поддержку; небезопасного
сброса только по номеру телефона нет.

### Единое расписание броней

Сайт и Telegram-бот используют таблицу `bookings` в одной SQLite-базе. Новая
или подтверждённая бронь занимает единственный стол на 120 минут. Сервер
проверяет пересечение внутри `BEGIN IMMEDIATE`, поэтому параллельные запросы не
могут создать двойную бронь. Статусы `cancelled` и `completed` освобождают
интервал. При попытке вернуть такую бронь в `new` или `confirmed` пересечение
проверяется повторно.

Публичная доступность содержит только время и не раскрывает данные гостей.
Сайт и бот показывают занятые старты недоступными, но окончательная проверка всё
равно выполняется при создании заявки. Бронь на 13:00 занимает 13:00–15:00 и
делает недоступными старты 12:00–14:30; следующий возможный старт — 15:00.

В разделе «Брони» панели владельца можно подтвердить, завершить или отменить
заявку, а также вручную закрыть произвольное получасовое окно — например, для
частного события. Закрытое время учитывается и сайтом, и ботом.

Бот создаёт бронь с заголовком `X-Booking-Bot-Secret`. Значение
`BOOKING_BOT_SECRET` должно быть случайным (рекомендуется `openssl rand -hex
32`) и одинаковым в `/etc/chainya-bot.env` и окружении `chainya-shop`. Без
секрета интеграция закрывается безопасно и бронь не считается принятой.

Сырые события статистики хранятся не более 360 дней.

Если заданы `BOT_TOKEN` и `OWNER_CHAT_ID`, после первого перехода заказа в
`paid` backend отправляет владельцам уведомление через Telegram. Повторный вызов
эндпоинта оплаты не дублирует сообщение.

## Saby Retail

Клиент `backend/saby.py` поддерживает сервисную авторизацию, точки продаж,
прайс-листы, каталог с ценами и остатками, компании, склады и создание заказа на
доставку. В коде настроено 29 стабильных соответствий `id` + `externalId`.
Позиция «Травяной сбор „Тонизирующий“» не связана с витриной по указанию
владельца; это не удаляет её из кассы.

Отдельный `SABY_CATALOG_SHADOW_MODE=on` запускает только чтение каталога при
старте сервиса и затем каждые 300 секунд. Результат сохраняется в SQLite (не
более 50 запусков) и показывается в блоке «Теневая сверка каталога» панели
владельца. Для весового товара сайт хранит цену за 10 г, поэтому она сравнивается
с ценой Saby за 1 г после деления на 10; для штучного товара цена сравнивается
один к одному. Наличие требует минимум 10 г или одну штуку. Неизвестные единицы
и остатки не угадываются, а помечаются как несравнимые.

Теневая сверка не вызывает API записи и никогда не обновляет каталог. Она не
зависит от `SABY_ORDER_SYNC_MODE` и не разрешает передачу заказов. Этот режим
должен оставаться `off`, пока поддержка не восстановит прайс-лист 7 в списке API,
не подключит точку к продукту `delivery` и владелец отдельно не разрешит
контролируемую запись.

Read-only снимок 05.08.2026: точка 274 и все 29 связей найдены, Saby отдаёт 30
товаров; совпадают 27/29 цен и 28/29 состояний наличия. Требуют проверки две
цены, отличающиеся в 10 раз, и отрицательный остаток одной активной позиции.
Каталог по `priceListId=7` читается, хотя endpoint списка прайс-листов возвращает
пустой результат. Автоматически подбирать другой прайс-лист нельзя.

Скопируйте значения из `backend/saby.env.example` в защищённый серверный файл
`/etc/chainya-shop-saby.env`. После добавления трёх ключей в админ-панели станет
доступна кнопка проверки подключения. После выбора точки и прайс-листа добавьте
`SABY_POINT_ID` и `SABY_PRICE_LIST_ID` и перезапустите `chainya-shop`.

## Т-Банк и CDEK

Шаблон новых параметров — `backend/integrations.env.example`, серверный файл —
`/etc/chainya-shop-integrations.env` с правами `0600`. Режимы по умолчанию:
`TBANK_CHECKOUT_MODE=off`, `CDEK_INTEGRATION_MODE=off` и
`SABY_ORDER_SYNC_MODE=off`. Безопасный `SABY_CATALOG_SHADOW_MODE=on` управляет
только периодическим чтением и не снимает ни один предохранитель записи.

Для локальной проверки поддерживается отдельный DEMO-терминал:
`TBANK_CHECKOUT_MODE=demo` разрешён только при `CHAINYA_TEST_MODE=1` и только
для ключа с суффиксом `DEMO`; Saby и CDEK при этом остаются заблокированы.
Боевой терминал работает только при `CHAINYA_TEST_MODE=0`,
`TBANK_CHECKOUT_MODE=auto` и полностью настроенном онлайн-чеке. Checkout
сохраняет `PaymentId`/`PaymentURL`, дедуплицирует повторный запрос по
`Idempotency-Key`, а оплатой считает только подписанный callback `CONFIRMED` на
`/api/payments/tbank/notification`. Страницы `/payment/success` и
`/payment/fail` сами статус не меняют.

Полный возврат тестового/боевого платежа доступен владельцу через
`POST /api/admin/orders/{id}/tbank/refund` и кнопку в панели. Повторный запрос
не создаёт второй возврат.

Код не разрешает боевой режим `auto` без полностью настроенного онлайн-чека:
после подтверждения СНО, ставок НДС и версии ФФД задаются `TBANK_RECEIPT_*` и
`TBANK_RECEIPT_ENABLED=1`; серверный чек передаётся в `Init`. При полном
`Cancel` структура чека по текущему контракту Т-Банка не передаётся: банк
формирует полный возвратный чек автоматически; для частичного возврата нужен
чек только с возвращаемыми позициями. 04.08.2026 представитель проекта
подтвердил УСН «Доходы», отсутствие НДС для чая и доставки и ФФД 1.05;
production-конфигурация совпадает с этими значениями. До первого реального
платежа всё равно нужен контролируемый тест по `ops/PRELAUNCH_CHECKLIST.md`;
менять защищённый env по догадке нельзя.

Ключи CDEK API хранятся только в `/etc/chainya-shop-integrations.env`.
Публичная корзина ищет города и ПВЗ через сервер, а цену считает по тарифам
«Посылка склад-склад» (136) и «Посылка склад-дверь» (137). Вес определяется по
фасовкам в корзине плюс `CDEK_PACKAGING_WEIGHT_G`; габариты задаются
`CDEK_PACKAGE_*`. При создании заказа сервер повторяет расчёт и проверяет, что
ПВЗ действующий и относится к выбранному городу.

Расчёт и справочники не создают внешних сущностей. Регистрация оплаченного
отправления доступна отдельной кнопкой владельца только после установки
`CDEK_SHIPMENT_POINT`, отключения общего тестового режима и явного режима
`CDEK_INTEGRATION_MODE=manual`. В `off`/`shadow` создание отправлений
заблокировано независимо от наличия ключей.
