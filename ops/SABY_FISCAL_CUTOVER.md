# Переключение фискализации с Т-Банка на Saby

## Обязательная защита остатка

- установить `SABY_STOCK_GUARD_MODE=auto` одновременно с live checkout;
- контрольная покупка должна использовать одностадийный `PayType=O` и перейти
  непосредственно в `CONFIRMED`;
- до открытия платёжной формы остаток должен быть подтверждён чтением Saby и
  зарезервирован локально на 15 минут;
- при нехватке до создания платежа checkout должен завершаться ошибкой 409;
- редкая офлайн-продажа после проверки и до оплаты требует обычного возврата.

Этот документ — production-runbook. Он не является разрешением на изменение
кассы. Переключение выполняется только в согласованное окно владельцем и
техническим ответственным.

## До окна

1. Отдельно подтвердить `SABY_POINT_ID`, `companyID` для метода
   `retail/sale/create` и регистрационный номер интернет-ККТ. Saby описывает
   `companyID` как идентификатор точки продаж и рекомендует уточнить точное
   значение у поддержки. Fail-closed политика Chainya требует, чтобы оба явно
   заданных значения совпадали; иначе checkout закрывается до проверки.
2. Убедиться в кабинете Saby, что ККТ зарегистрирована для расчётов в интернете,
   смена открывается штатно, а электронный чек отправляется покупателю.
   Предупреждение Saby об устаревшей прошивке ККТ должно быть устранено до окна.
3. Бухгалтер подтверждает: УСН «Доходы», без НДС и фискальную схему отдельно
   для немедленной выдачи, отложенного самовывоза и CDEK. Текущий код можно
   включать только если для разрешённых потоков подтверждён один чек «полный
   расчёт» после оплаты; иначе сначала реализуется схема предоплаты и чека при
   передаче. Также подтверждается порядок полного возврата.
4. Зафиксировать точное время отсечки в ISO-8601 с часовым поясом. Старые и
   тестовые оплаты не должны попасть в Saby автоматически.
5. Сделать согласованный snapshot базы и защищённых env. Не копировать секреты
   в Git, логи или этот документ.
6. Проверить полный тестовый набор и отсутствие секретов в diff.
7. В админ-панели запустить read-only проверку Saby. Поле
   `fiscal_probe` должно подтвердить доступ к компании. Состояние
   `separate_auth_required` ожидаемо: документированный список ККТ
   использует отдельную OFD-сессию (`sid`), а не сервисный OAuth Retail.
   Оно не подтверждает и не опровергает готовность кассы и не является
   поводом повторять продажу.

Read-only проверка Retail не создаёт чек и не заменяет один согласованный
контрольный платёж. Новый платёж не используется как способ диагностики
неподтверждённой конфигурации.

## Атомарное переключение

1. Закрыть публичное создание новых оплат только для Chainya.
2. Дождаться завершения уже открытых платёжных сессий либо явно сверить их.
3. Отключить формирование онлайн-чека на терминале Т-Банка. Эквайринг оставить.
4. В защищённом env установить:

   ```text
   TBANK_RECEIPT_ENABLED=0
   SABY_PURCHASE_ROUTE=fiscal_sale
   SABY_ORDER_SYNC_MODE=auto
   SABY_ORDER_SYNC_STARTED_AT=<согласованная отсечка ISO-8601>
   SABY_OFD_COMPANY_ID=<подтверждённый companyID для retail/sale/create>
   SABY_OFD_KKT_REG_NUMBER=<из Saby>
   SABY_OFD_TAX_SYSTEM=2
   SABY_OFD_PAY_METHOD=4
   SABY_OFD_ALLOW_NEGATIVE_STOCK=0
   ```

5. Перезапустить только backend Chainya согласованной production-командой.
6. Проверить secret-free статус интеграций: checkout доступен, маршрут
   `fiscal_sale` готов, чек Т-Банка выключен, отсутствуют blockers.
7. Открыть публичную оплату и выполнить один согласованный контрольный заказ на
   минимальную реальную сумму.
8. До следующего заказа подтвердить `CONFIRMED` в Т-Банке, состояние
   `registered` у продажи и чек в Saby/ККТ/ОФД.
9. После закрытия смены подтвердить корректное складское списание.

## Fail-closed состояния

- `blocked`: не хватает настройки или одновременно включены два источника чека;
  публичный checkout не должен открываться.
- `failed`: запрос точно не был отправлен (например, локальная валидация); после
  исправления причины возможен контролируемый повтор.
- `ambiguous`: ответ Saby потерян после отправки. Автоматический повтор запрещён,
  пока операция не сверена в Saby по `externalId` и времени.
- `pending_ofd`: Saby принял продажу и вернул идентификатор, но фискальный
  признак ещё не появился; backend выполняет только GET-контроль и не создаёт
  продажу повторно. Изменение маршрута для новых заказов не перенаправляет уже
  полученный `payId` в Delivery.
- `registered`: GET-контроль Saby вернул непустой фискальный признак.

Фоновая очередь автоматически возобновляет только доказанно локальный
`blocked` фискального маршрута: его конфигурация уже исправлена и готова к
записи, а у операции нет ни `payId`, ни сохранённого хеша payload. Наличие
любого из этих признаков исключает автоматический повтор. Delivery этой логикой
не возобновляется, потому что его доступность определяется внешним запросом.
Это позволяет восстановиться после исправления env без ручной правки SQLite и
не ослабляет запрет повторов для `ambiguous`/`pending_ofd`.

Если владелец письменно принимает временную ручную фискализацию, можно задать
`SABY_AMBIGUOUS_CHECKOUT_POLICY=manual`. Тогда уже сохранённые `ambiguous` не
закрывают новые платежи, но остаются в панели и не повторяются. Владелец обязан
вручную провести и сверить каждый такой заказ; возвраты остаются отдельной
операцией. Значение `block` является безопасным режимом по умолчанию.

Состояние `ambiguous` нельзя повторять из панели: ответ мог потеряться после
того, как Saby уже принял продажу. Такой заказ остаётся видимым для ручной
сверки и отдельного решения владельца с техническим ответственным; штатная
очередь второй `POST` не выполняет.

Обновление кода не меняет это правило. Существующая запись `ambiguous` с
сохранённым хешем payload и без `payId` остаётся неизменной после перезапуска
worker: новый формат payload применяется только к новым заказам после отсечки.
Старые неопределённые операции нельзя «исправлять» повторной отправкой новым
форматом.

Текущий кандидат следует опубликованному JSON-примеру
`retail/sale/create`: неиспользуемые суммы оплаты/НДС и отсутствующие
email/ИНН передаются как `null`, дополнительный реквизит заказа — как
`propVal`. Это изменение wire-формата само по себе не доказывает устранение
HTTP 500: доказательством служит только один отдельно согласованный новый заказ
после установки кандидата и подтверждение его `payId`, фискального признака и
складского списания.

При одностадийной схеме отдельного окончательного чека при выдаче нет: основной
чек уже содержит `payMethod=4`. Старый endpoint окончательного чека закрыт и не
может создать повторную продажу.

## Возврат

Полный возврат сначала подтверждается Т-Банком. Только после статуса `refunded`
и зарегистрированного чека продажи создаётся один возвратный чек Saby с
отдельным стабильным `externalId`. Частичный возврат автоматически
заблокирован и требует отдельной подтверждённой бухгалтером схемы.

## Rollback до первой успешной продажи

1. Снова закрыть новые оплаты Chainya.
2. Вернуть прежний источник чека Т-Банка и его подтверждённые параметры.
3. Установить `SABY_ORDER_SYNC_MODE=off` и `SABY_PURCHASE_ROUTE=delivery`.
4. Перезапустить только backend Chainya и проверить checkout/status.

## Rollback после хотя бы одной продажи

Автоматически откатывать источник чека нельзя. Сначала нужно сверить все оплаты
после отсечки с T-Банком, Saby и ОФД, завершить или вручную разобрать каждое
состояние `sending`/`ambiguous`, затем выбрать новую отсечку. Иначе возможны
пропущенные или двойные чеки.
